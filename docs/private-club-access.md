# Private club entrance and staff access

`CLUB_GATE_ENABLED=true` shows the shared invitation entrance to first-time guests. Returning admitted browsers and active members skip it. `/login`, `/forgot-password`, `/reset-password` and `/verify-email` remain directly accessible, including their form submissions, so existing members/admins can always use personal credentials. Signup separately checks invitation server-side, including when its action is posted to an otherwise public login URL. Entrance admission does not authenticate a member or grant staff permissions. The shared password remains rate-limited by a database counter (10 attempts per IP per 15 minutes), accepts only same-origin JSON and checks a cost-12 bcrypt hash server-side.

Set `CLUB_PASSWORD_HASH` as a Worker secret and GitHub repository secret. Use a long randomly generated invitation passphrase; do not put the plaintext or hash in client code, source files, build logs or public documentation. Staging uses its own `WALLET_TEST_CLUB_PASSWORD_HASH`, injected as `CLUB_PASSWORD_HASH` in the isolated Worker.

The correct password permanently remembers the current public IP in `ClubAdmission`, until the invitation password or `AUTH_SECRET` changes. Only an HMAC-SHA256 fingerprint and admission timestamp are stored, never the raw IP. The fingerprint includes the current invitation hash, so rotating that hash revokes both remembered networks and cookies. IP addresses identify networks, not people: everyone behind the same Wi-Fi, VPN or shared public IP can enter after one successful admission; reassigned IPs inherit network admission until rotation. A returning browser stays admitted when its IP changes. Personal login and staff authorization remain mandatory.

An HttpOnly, Secure, SameSite=Lax signed browser cookie lasts one year, independently of the current IP. Previously issued cookies retain their original expiry and remain accepted. Valid cookies avoid a database lookup on ordinary visits. Successful personal sign-in refreshes this browser admission. If only a personal session remains, the entrance checks current active account status and session version before issuing admission; suspended, closed, revoked or forged sessions cannot open the club. Logout removes personal access while preserving the browser's invitation. After cookie expiry/deletion or switching browsers, a remembered IP restores admission; otherwise members can sign in normally without the shared password. Database lookups/writes fail closed on errors; unknown/invalid IPs are never remembered as a shared fallback. Only Cloudflare's deployment-supplied `CF-Connecting-IP` is trusted for permanent network admission, excluding Worker subrequests and private/invalid addresses. Arbitrary forwarded headers cannot grant admission.

Missing or malformed configuration fails closed. Set the replacement GitHub secret and deploy to rotate. The entrance has its own JWT issuer/audience and cannot be used as a login session. Changing `AUTH_SECRET` also revokes all member sessions. Old fingerprints are unusable after rotation and may be cleared from `ClubAdmission` by the operator. Returning visitors are redirected away from `/entrance` to their requested page, personal login or dashboard. Old `preview=1` links no longer force the invitation to reappear.

With the lock enabled, robots disallows the entire site, the sitemap is empty and HTML responses are noindex/no-store. Existing search listings may take time to disappear. Public artwork, icons and application code remain downloadable. Cron and payment webhook endpoints retain their own independent secret/signature authentication; they do not accept the shared entrance password as authorization.

Admission lookups and idempotent inserts retry one transient HTTP failure, with a fresh five-second timeout for each of at most two attempts. A second failure still refuses admission. This also safely handles a stored admission whose response was lost; the unique fingerprint prevents duplicate rows. Valid browser cookies continue to avoid database lookups.

## Staff authority

- **Super Admin:** the existing protected owner account. Can approve/reject deposits, manage users/roles, reconcile payments, review trading, record results/payouts and edit plans/videos. Elevating another member to Super Admin is not available in the interface or role-management function.
- **Admin:** read-only access to club/member records after password and second-factor confirmation. Cannot approve/reject deposits or make any back-office changes. Can manage their own passkeys and recovery codes.
- **Member:** manages their own account, deposits and allocation requests under existing ownership and balance rules.

Server actions check current Super Admin authority. Atomic database management/financial functions independently recheck it while holding account locks. Read-only UI hides review/edit controls; disabled fields alone are not the security boundary. Owner promotion/demotion controls remain audited, password-confirmed and restricted to verified active members who have already signed in.

Validation covers direct action calls, database denials, unchanged financial balances, cookie forgery/expiry/rotation, member authorization after admission, cross-origin requests, input limits, throttling and direct/RSC/server-action gate enforcement. Deployment probes check locked routes, crawler policy, entrance assets and independent cron authentication.
